## 2. Why the deployment failed

Merge commit `bfdfc26` was pushed to `main` at 11:18:36Z and started the `Deploy`
workflow. The remote deployment aborted 1 m 26 s in, at the migration step:

```
+ applying the migrations (one-shot container)
unknown flag: --no-build
Error: Remote deployment failed, timed out, or lost its connection.
```

`infra/scripts/deploy.sh` invoked
`docker compose run --rm -T --no-build --pull never migrate`, and
`docker compose run` has **no** `--no-build` flag; that flag exists only on
`docker compose up`. Reproduced against Docker Compose 2.40.3:

```
$ docker compose run --no-build ...      → unknown flag: --no-build
$ docker compose run --pull never ...    → flag accepted (fails later on unrelated config)
```

Because the abort happens at step 2 of 6, the following never ran: the one-shot
migration container, `compose up` of the new API, the health check, and the
nginx activation with the new web image.

### Why the resulting state is safe

- `git diff 5e7db75..bfdfc26` touches **no** `backend/prisma` or migration file, so
  the migration that never ran would not have changed the schema. There is no
  "database ahead of the running code" drift.
- The pull of all three pinned images succeeded (they are on the host), so the
  failure left a **full disk**, not a partial layer; the API and nginx containers
  still run the `5e7db75` images.
- The server checkout advanced to `bfdfc26` before the abort, so the host holds
  that commit's scripts while its containers run the previous release. The next
  deployment's `--ff-only` merge will simply move on to the newer commit.

## 4. The fix

Branch `fix/deploy-migrate-compose-flags`, one commit:

- `infra/scripts/deploy.sh` — the migration run is now
  `compose run --rm -T --pull never migrate`. `--pull never` is kept: the image
  was already pulled under its pinned commit tag, and compose would otherwise
  fall back to `latest`. A comment records why `--no-build` must not be added.
- `infra/tests/test_deploy_runner.py` — the regression test asserted the invalid
  invocation verbatim, which is why CI stayed green while every deploy failed.
  It now asserts the CLI contract: no `compose run` line may carry `--no-build`,
  and the migration run must stay pinned with `--pull never`.
- `docs/DEPLOY_RECOVERY.md` — the prerequisites list now says `up --no-build`,
  `run --pull`, and `up --wait`.

Local result: `python3 -m unittest discover -s infra/tests` → **25 tests, OK**
(24 before, plus the new contract test). `bash -n infra/scripts/deploy.sh` is clean.
Shellcheck was not available in the working VM; CI runs it.
