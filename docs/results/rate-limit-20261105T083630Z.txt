Captured: 2026-11-05T08:36:30Z (UTC)

WHY THIS FILE EXISTS
  The resume line about the API rate limit had no artifact behind it, and a
  check of the code showed the limiter only counted: the throttler was
  configured without a block duration, which is what produces a 429.
  The fix (THROTTLE_BLOCK_MS, default 60 s) plus its regression test landed
  before this run. This is the measurement, produced by the suite itself.

COMMAND
  cd backend && THROTTLE_LIMIT=300 npm run test:e2e -- rate-limit

WHAT IT DOES
  Boots the real AppModule (global UserThrottlerGuard, in-process store) with
  the production default of 300 requests per 60 s, signs in three users from
  the SAME client address, spends 3 requests as the first user, then issues
  300 authenticated requests with a fresh token before the 301st.

RESULT
  - requests   1..300 -> 200 OK
  - request      301  -> 429 Too Many Requests, Retry-After: 60
  - a colleague behind the same IP, after the block -> 200 OK
    (the bucket is keyed on the verified user, not the address)
